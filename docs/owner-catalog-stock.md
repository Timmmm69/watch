# Управление часами и остатками в существующей админке

Реализовано поверх текущих CatalogService, AssetService и NativeInventoryService.
Отдельного магазина, источника остатков или новой схемы денежных расчётов нет.

## Владельцу

1. Откройте **Каталог → Добавить товар**. Введите название, бренд, цену в рублях,
   начальное количество и описание. Категорию можно выбрать сейчас или позже.
   Артикул создаётся автоматически. Нажмите **Сохранить черновик и добавить фото**.
2. Выберите несколько фотографий, нажмите **Загрузить выбранные фото**.
   **На обложку** делает фото первым; **В конец** меняет порядок. Лишнее фото можно
   убрать. Если опубликованной карточке нужно удалить последнее фото, сначала скройте её.
3. В дополнительных настройках цены укажите согласованную цену для продавца.
   Она обязательна по существующим правилам магазина; автоматически подставлять
   розничную цену система не будет. Комиссии и расчёт с поставщиком остаются отдельными.
4. Основные поля сохраняются автоматически. Дождитесь **Сохранено**, посмотрите
   **Предпросмотр**, нажмите **Опубликовать**. При неполной карточке появится список
   того, что нужно исправить. Нулевой остаток не препятствует публикации.
5. Новая поставка: в карточке или разделе **Склад** выберите **Добавить поступление**,
   введите количество и основание, проверьте результат и подтвердите. При списании
   выберите **Списать**. При пересчёте вводится новое физическое количество, а не разница.
6. **Скрыть** возвращает карточку в черновик, **В архив** сохраняет историю.
   Заказы обрабатываются в существующем разделе **Заказы**.

При сбое сети форма и выбранные файлы остаются на экране. Повторите сохранение
или загрузку. Не закрывайте страницу с незагруженными файлами: приложение предупредит,
что их потребуется выбрать заново. Несохранённые основные поля сохраняются на устройстве;
после перезагрузки доступно явное восстановление. При редактировании из нескольких окон
конфликт показывает ошибку, а не затирает чужую версию.

## Тестовые часы

Каталог → **Тестовый каталог → Добавить тестовые часы** с явным подтверждением.
Это штатное действие авторизованного администратора, доступное и после установки
на рабочем сервере. Оно добавляет 8 опубликованных карточек, 6 брендов, 3 тестовые
категории, 29 единиц; одна модель имеет 1 шт., одна — 0. Все карточки помечены
**ТЕСТ**, описания сообщают об иллюстративных фото и тестовых ценах/остатках.

Данные и три фотографии выборочно взяты из PR #16; сам PR не слит. Его CLI,
ограничение пустой базой и отдельный seed-процесс не используются. Наше действие
работает рядом с существующим каталогом, не создаёт пользователей/сессий, не
подставляет закупочную стоимость и не меняет существующие карточки или остатки.
Повтор после списаний/заказов/изменения цены возвращает прежний результат.
Коллизия тестовых артикулов/категорий блокирует весь запуск. При сбое записи
транзакция откатывается, новые файлы удаляются по возможности.

## Хранение и переход без Google

- Остаток существует только в существующем PostgreSQL ledger: initialization,
  receipt, correction, reserve, release, shipment. Цена/описание не создают движений.
- Физический остаток, активные резервы и доступность читаются из существующих
  inventory_items. Списание не затрагивает зарезервированные единицы.
- Поступление без закупочной стоимости оставляет её неизвестной. Оно не создаёт
  продажу, денежное поступление или комиссию. Пересчёт проверяет старое физическое
  количество под блокировкой; при изменении требует повторной сверки.
- Новый migration `20261103160000_owner_catalog_operations` добавляет таблицу
  ключей повторов. Старые миграции и коммерческая история сохранены.
- Сервер уже требует `INVENTORY_PROVIDER=native`; runtime не запускает Google sync
  и игнорирует неиспользуемые Google credentials. Приложение работает без них.
  Обычная админка больше не предлагает синхронизацию или ручные служебные ключи.
- Google-таблица не удаляется и не изменяется. При необходимости реального переноса
  остаётся существующий preview → confirmation → apply из `native-inventory-t47.md`.
  Автоматического или повторного переноса в этой доработке нет.

## Установка

Применить новую миграцию штатным процессом релиза и собрать API/web из этой ветки.
Docker API image включает фотографии фикстур. Войти обычной авторизацией
Telegram с существующим Admin и открыть `/admin/catalog` либо `/admin/inventory`
на текущем домене магазина. Бота и его меню эта доработка не перенастраивает.

На дату разработки доступен GitHub, но отсутствует подключение к серверу,
рабочей БД, медиа-хранилищу и авторизованной Telegram-сессии владельца.
Рабочий магазин и реальные товары не менялись. Тестовый каталог добавлялся через
настоящие API и интерфейс в изолированные тестовые схемы. Для применения нужен
защищённый доступ к существующему серверу развёртывания, а не передача секретов в чат.

## Проверки и границы доказательств

Команды API выполняются из `apps/api` с настроенными одноразовыми локальными
`TEST_DATABASE_URL`, `WATCH_T47_DATABASE_URL` и `WATCH_T48_DATABASE_URL`:

```sh
pnpm exec vitest run src/catalog/owner.integration.test.ts src/catalog/catalog.test.ts src/catalog/media-upload.test.ts src/catalog/native-price.integration.test.ts src/inventory/native.integration.test.ts src/inventory/runtime.test.ts src/orders/referral-native.integration.test.ts src/orders/fulfillment.integration.test.ts
```

Браузер из `apps/web`, API на 3001 поднимается самим fixture:

```sh
pnpm exec playwright test tests/admin-catalog.spec.ts tests/admin-inventory.spec.ts tests/admin-orders.spec.ts tests/fulfillment.spec.ts tests/referral-native.spec.ts --workers=1
```

Также: workspace typecheck, production build API/web, Prisma validate,
проверки runtime config без Google credentials и `git diff --check`.

Реальный PostgreSQL 16.15; в UI-тестах реальны сессии, CSRF, авторизация Admin,
API, SQL-транзакции и загрузка файлов multipart. ObjectStorage в тестах —
память на границе S3; ответ Telegram SDK заменяется пустым скриптом, API админки
не подменяется. Только тесты потери ответа намеренно обрывают ответ после
настоящего commit. Старые тесты admin-orders отдельно используют API mocks.

Не проверены рабочий сервер/реальный S3, устройство Telegram и экранная клавиатура,
Docker image build (Docker здесь отсутствует), внешняя сеть магазина и фактический
экспорт старой Google-таблицы. Первичный общий запуск старого набора не является
сертификацией: legacy suites требуют предварительно мигрированную public-схему,
а часть аналитики имеет фиксированные октябрьские периоды. Итоговый прогон ограничен
затронутыми сценариями и совместимыми native suites с миграциями в каждой новой схеме.

Итоговый целевой прогон: 76 проверок API/склада/заказов и 50 проверок конфигурации прошли; 17 браузерных проверок прошли: 12 используют настоящий API/PostgreSQL (админка, покупательский checkout, отправка, отмена, возврат), 5 существующих проверок admin-orders используют API mocks. Typecheck, production build API/web и Prisma validate — успешно.
