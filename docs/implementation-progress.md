В DROPSHIP_MARKUP buyer_user_id=NULL, creator_user_id принадлежит partner_id_snapshot через составной FK. Тот же Partner используется существующими Commission и Ledger; отдельного владельца или финансового баланса не создано.

При наличии privacy acknowledgement его актор — creator; актуальность документов и права проверит T48. Получатель — существующий OrderFulfillmentDetail, без User/Telegram/фиктивного согласия. Отложенные ограничения требуют непустые имя, телефон, адрес и согласованный итог строк; штатная редакция PII сохраняется.
- Отдельная D в ProductVariant, неизменяемые D/R/количество/общая выделенная C/общая наценка строки. Для нового режима unit_price_minor=R, partner_commission_unit_snapshot_minor=R-D, remuneration_total_minor=(R-D)*q. Эти поля имеют соответствующий смысл и в существующем Commission; supplier-settlement не переименован в C/D и остаётся пустым у новых строк. R>=D, q=1..99, сумма заказа <=2 000 000 000 копеек. C может быть NULL (неизвестна), 0 (известный ноль) или положительной INTEGER-суммой.
- В InventoryItem добавлены независимые native on-hand, резервированное количество, стоимость свободного пула, известная стоимость резервов и количество резервов с неизвестной стоимостью. До явной инициализации все native-поля NULL. Старое source_quantity не перенесено в физический остаток.
- Неизменяемые InventoryInitialization / InventoryMovement: актор, причина, occurrence time, устойчивый ключ операции, SKU, последовательность, связи с резервом/ReturnItem и итоговые количество/стоимость. Один SKU нельзя инициализировать повторно; исходный резерв допускает одно создание и один терминальный эффект. Проекция и журнал должны совпадать при COMMIT; прямое изменение native-остатка без движения отклоняется.
- Журнал представляет поступление, оценку, коррекцию, резерв, освобождение, отправку, физическую инспекцию возврата и подтверждённую потерю отправленного товара. SHIPMENT_LOSS не означает физическую приёмку и не прибавляет остаток. У инспекции отдельно записаны полученное пригодное количество и его стоимость; остаток инспекции — непригодные часы/потеря. Неисполненный или только финансовый возврат сам не создаёт складского факта.
- Копеечное распределение закреплено SQL-функцией procurement_slice и ограничениями журнала; bigint используется только для промежуточных произведений. Полный резерв получает весь V, частичный — floor(V*q/Q). Освобождение возвращает первоначальную C, отправка удаляет её из резервов. Возвраты/подтверждённые потери используют накопительное распределение исходной C; совокупное количество ограничено строкой и ReturnItem. Уже использованный ReturnItem защищён от изменения.
- Неизвестная стоимость распространяется на смешанный свободный пул; известное поступление само её не устраняет. Старые известные резервы сохраняются. Новый известный базис возникает только при документированной полной оценке свободного текущего остатка либо исчерпании старого свободного пула и известном поступлении. Пустой пул имеет известный 0; исторические неизвестные снимки не дополняются оценкой.
- Append-only OrderMoneyEntry, CustomerObligation, OrderDirectExpense, OrderExpenseReview. Деньги имеют уникальные ключ операции/reference; корректировка полностью сторнирует одну исходную запись, повтор и корректировка чужого заказа запрещены. Возврат денег ссылается на подтверждённое обязательство того же заказа и не может превысить остаток обязательства. Снижение обязательства также ограничено непогашенным остатком. Переплата — обязательство, а не наценка.
- Прямые расходы — фактически оплаченные доставка/упаковка/платёжная комиссия/прочие внешние затраты, со связью со строкой при необходимости. Сторно отдельной записью. ExpenseReview фиксирует число записей и их сумму; отсутствие review отличается от явно проверенного нуля. Новые расходы делают старый review неполным.
- Новые факты защищены триггерами UPDATE/DELETE/TRUNCATE; app-grants дополнительно отзывают эти права у watch_app. Сохранены существующие защиты ledger/allocations. Режим старой строки нельзя переименовать в новый, native-снимки и стоимость резерва нельзя исправить задним числом.

### Контракт для последующих задач

Полная физическая стоимость известна, если free_value не NULL и reserved_unknown_quantity=0:
`physical_value = free_value + reserved_known_value`. В остальных случаях она неизвестна; известная часть резервов остаётся доступным отдельным фактом. INTEGER-стоимость складского состояния ограничена 2 147 483 647 копейками.

На заказе: `cash = SUM(OrderMoneyEntry.amount_minor)`, где receipt положителен, refund отрицателен, correction — обратная сумма исходного факта. Для каждого исходного обязательства:
`outstanding = original_amount + SUM(obligation_adjustments) + SUM(linked_refunds_and_their_corrections)`.
Для покрытия T50 использует `cash - SUM(outstanding) >= retained_R_sales`. Уже выплаченный refund уменьшает одновременно cash и outstanding; повторно вычитать первоначальную сумму обязательства нельзя. Эта проверка не создаёт частично оплаченную комиссию; существующие delivery/hold/affected-return gates обязательны.

Расходы и покрытие данных не выводятся из наличия денег или статуса заказа. Для актуального expense review должны совпадать число записей и сумма журнала. Убыток возвращённого непригодного/утраченного товара выводится из исходной распределённой C и соответствующего складского факта; не вводится вторично как внешний денежный расход. Финансовый возврат не является прямым расходом. Owner contribution использует D по сохранённым товарам, их C и отдельные реальные расходы/потери; R-D не вычитается из D второй раз.

Факты не исполняют бизнес-операции автоматически. T47/T49 должны в одной транзакции согласовывать статусы резервов/заказа, journal и проекцию, соблюдать общий порядок блокировок и создавать audit/outbox. T50 должен сериализовать Partner→Order, проверять денежное покрытие и текущие возвраты перед release/выплатой. Наличие схемы не включает новый режим в работающем приложении.

Избыточные деньги не увеличивают коммерческий снимок, наценку или маржу.
- Расходы изначально NULL/«не проверены», включая пустой журнал. Админ может явно подтвердить 0. Подтверждение связано с текущими количеством записей и суммой; новый расход/сторно делает прежнюю проверку неактуальной, устаревший review отвергается. Возмещение покупателю, складская потеря и наценка не добавляются повторно как внешний расход.
- Существующие Commission/Ledger/Payout/allocations сохранены. Наценка берётся из уже неизменяемого T46/T48 снимка R−D конкретной строки. Новый release проверяет DELIVERED, исходный hold (по умолчанию 14 календарных дней), eligible_at, отсутствие REQUESTED по своей строке и `cash − непогашенные обязательства >= retainedR` всего заказа. Частичная оплата не дробит начисление. Непокрытый доставленный Order остаётся DELIVERED для следующего worker scan. Незатронутые строки могут высвобождаться; отклонение после hold не меняет первоначальный срок.
- Денежные операции, Return, release и выплаты сериализуются тем же Partner lock и существующим порядком Order/OrderItems/catalog/inventory. При создании выплаты проверяются все нераспределённые кредиты: непокрытая наценка не может компенсировать прежний долг ради выплаты других средств. Перед PAID повторно проверяются текущие allocations, покрытие, возвраты и отрицательный AVAILABLE. Изменившиеся факты блокируют выплату: старую заявку можно отклонить и создать новую на актуальный баланс.
- PAID — прежнее явное подтверждение внешнего перевода с безопасным reference; реальные перечисления приложение не выполняет. Изменённый reference при replay конфликтует. Новое уникальное verified_transfer_reference защищает новые подтверждения, в том числе разных партнёров, сохраняя старые поля/выплаты с NULL в новом поле. Поздний возврат сохраняет PAID/allocations/исходный payout ledger и добавляет отрицательный AVAILABLE/долг; новые доходы его компенсируют.
- В партнёрских доходах и перед суммой выплаты отдельно видны долг и учтённые сторно; непокрытые кредиты/REQUESTED блокируют запрос. Новый денежный блок переиспользует существующий Session/CSRF recovery карточки заказа и очищается вместе с защищёнными сведениями при отказе доступа.
- Миграция `20261016030000_observed_money` установлена с нуля и на репрезентативные T49 факты. Для ранее завершённых native Returns дописывает отсутствующие обязательства без фиктивного cash refund. Прежние снимки, комиссии, cash, ledger, Returns и allocations сохранены. Старые миграции T46–T49 не переписаны. Readiness требует T50 migration.

Дропы: создано/незавершено/доставлено, удержанные заказы/единицы/D, вклад владельца, наценка, отмены/невыкупы/возвраты и расчёты. Полный возврат из DELIVERED также закрывает исход, не придумывая удержанную продажу.
- Europe/Minsk, местные полуночи, полуоткрытый период, пресеты 7/30 дней. Отдельный поток `delivered_at` учитывает единицы после возвратов до доставки и не пересчитывается поздними возвратами. Денежные RECEIPT/REFUND/CORRECTION группируются по `occurred_at`, независимо от когорты. Текущие очереди/обязательства/склад явно подписаны «все даты»; несовместимые совокупности не вычитаются друг из друга.

Непригодная часть остаётся потерей, без повторного вычета. Неотправленная отмена не расходует закупку. Общие расходы между SKU распределены по исходным единицам, с сохранением копеек. Неизвестная C, устаревший/отсутствующий review расходов, открытый Return или незавершённая приёмка исключают заказ из покрытой части; проверенный 0 известен. Полный вклад доступен только при полном покрытии, отдельно показаны покрытая сумма и число заказов; пустой знаменатель — «Нет данных».
- LEGACY_FIXED не получает выдуманные D/R/C: количество исключённых из новой экономики заказов показано явно, исторические экраны и балансы расчётов сохранены. Основной native-экран не требует реферальной/регистрационной воронки.
