# Рабочий обзор и аналитика владельца — T51

В native-режиме существующие `/admin` и `/admin/analytics` открывают отчёт владельца. Источники — PostgreSQL T46–T50: коммерческие снимки OrderItem, native-склад/приёмки, Returns, ручные деньги, расходы и их проверка, существующий Commission/Ledger/Payout. Google Таблица не участвует в текущих остатках или отчётах. Исторические экраны прежнего режима сохранены.

## Какое решение принять

| Отчёт | Практическое действие |
|---|---|
| Рабочие очереди | Обработать новый/зависший заказ, проверить недостающую оплату после доставки, завершить возврат/приёмку/возмещение, разобрать заявку выплаты или ошибку склада. Каждый счётчик открывает именно свой список, затем существующую карточку. |
| Удержанные завершённые продажи | Оценить результаты созданных в периоде заказов, отдельно от незавершённых и суммы созданных заказов по R. |
| Вклад закрытой когорты | Проверить, покрывают ли D закупку, расходы и потери; найти заказы с неизвестной стоимостью, непроверенными расходами или незавершённой приёмкой. |
| Расчёты с дропами | Планировать выплаты по состояниям журнала; видеть уже перечисленное, занятое заявками и долг каждого дропа без взаимного зачёта разных людей. Предупреждение показывает блокировку выплаты по текущим фактам T50. |
| SKU | Пополнить продающиеся товары, сопоставить удержанные продажи с текущим наличием/резервами, разобрать возвраты и вклад. Нулевые продажи сами по себе не доказывают залежалость. |
| Дропшипперы | Сравнить созданные и удержанные результаты, вклад владельца, наценку дропа, отмены/невыкупы и возвраты; открыть карточку для работы с конкретным дропом. |
| Поток доставок | Оценить фактический объём доставок в периоде, независимо от даты создания заказа. |
| Денежный поток | Проверить фактические поступления, возмещения и корректировки за период; не приравнивать их к прибыли или результату когорты. |
| Сверка с заказами | Найти заказ, объясняющий итог/неполное покрытие, и открыть его операционные и финансовые формы. |

## Совокупности и расчёты

- Рабочий пояс **Europe/Minsk**. Даты формы задают местные полуночи, начало включительно, конец исключительно; доступны последние 7/30 дней. API принимает точные временные границы, максимум 365 дней.
- Когорта качества — `created_at` в периоде и текущие исходы. Удержанные продажи — только COMPLETED с положительным количеством после **COMPLETED** Returns. REQUESTED/REJECTED не уменьшают проданные единицы. Свежие DELIVERED, в том числе с hold/неполной оплатой, остаются незавершёнными.
- Закрытая экономика включает COMPLETED/CANCELLED/исторические DELIVERY_FAILED, а также полностью завершённый возврат из SHIPPED/DELIVERED. T49 сохраняет отказанный native-заказ SHIPPED без искусственной доставки: полный возврат без `delivered_at` считается невыкупом. Открытая физическая приёмка делает его вклад неизвестным. Такой заказ не остаётся в очереди зависшей доставки; приёмка/возмещение остаются в очереди возвратов.
- Вклад = **D удержанных единиц − исходная C отправленных единиц + стоимость фактически принятых пригодных возвратов − фактические прямые расходы этих же заказов**. Это также C удержанных единиц плюс невозмещённая C потерь; повторно вычитать складскую потерю нельзя. Неотправленная отмена не расходует закупку. Расходы отмен/невыкупов не исчезают из закрытой когорты. R−D не вычитается из D повторно.
- Неизвестная C, отсутствующая/устаревшая проверка расходов, открытый Return или ещё не определённая физическая судьба возвращённых единиц исключают заказ из покрытой части. Проверка расходов сверяет текущие количество записей и сумму с последним review T50; подтверждённый 0 известен. Поздняя оценка текущего склада не исправляет старую неизвестную C. При нулевом числе закрытых заказов вклад/доля покрытия — «Нет данных».
- Полный вклад доступен только при покрытии всех закрытых заказов. Отдельно названы покрытая сумма и число покрытых/всех закрытых заказов. Это вклад до налогов и постоянных расходов, а не чистая прибыль магазина.
- Общие расходы заказа распределяются между SKU по **исходному количеству** с накопительным целочисленным округлением в порядке OrderItem ID; возврат не переносит весь расход на оставшийся товар. Если весь заказ не покрыт, его SKU-вклад также не выдаётся за полный. Число заказов покрытия разных SKU может пересекаться; суммы вкладов/продаж сходятся со сводкой. Детализация по дропам использует те же заказы и вычисленные суммы.
- Поток доставок использует `delivered_at`; единицы исключают возвраты, завершённые **до доставки**, но не последующие возвраты. Денежный поток использует `OrderMoneyEntry.occurred_at`: RECEIPT, REFUND и CORRECTION показаны отдельно. Эти потоки не подставляются в формулу вклада когорты.
- Расчёты с дропами и склад — **текущее состояние по всем датам**, явно отделённое от периода. Балансы PENDING/AVAILABLE берутся из существующего Ledger, занято заявками/выплачено — из REQUESTED/PAID. Долг считается отдельно по каждому Partner; поздний возврат не уменьшает исторический PAID. Признак блокировки использует тот же `commissionPayable`, что T50.
- Исторические LEGACY_FIXED не получают выдуманные D/R/C: в новой экономике они исключены с явным количеством. Их существующие балансы расчётов сохраняются в текущих обязательствах.

## Рабочие списки и доступ

`GET /api/v1/admin/analytics/owner?from=…&to=…` — сводка, SKU, дропы и сверка заказов; `GET /api/v1/admin/analytics/work?queue=new|overdue|unpaid|returns|payouts|inventory&page=1&limit=20` — страницы очереди. Лимит до 100; счётчик/список используют одинаковые SQL-предикаты. Возвраты включают REQUESTED и COMPLETED с ожидающей физической приёмкой или денежным возмещением. Складские ошибки — неинициализированный SKU, дефицит относительно резерва/буфера или несогласованный резерв; неизвестная закупка сама по себе не выдаётся за ошибку количества.

Каждое чтение выполняется в одной read-only REPEATABLE READ транзакции. Доступ — только текущие Session/Admin, ответ `no-store`. При отказе доступа интерфейс очищает защищённые данные; Session recovery повторяет чтение. Новые операции денег/склада/выплат не добавлены: используются карточки T47–T50.

Проверка выполняется только на disposable локальных PostgreSQL-схемах. Примеры, test fixtures и снимки в `outputs/t51/` — **тестовые**, не фактические результаты магазина. Production, реальный импорт, Telegram и переводы относятся к T52 и этим отчётом не сертифицируются.
