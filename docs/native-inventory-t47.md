# T47 — внутренний склад и первоначальный импорт

Источник требований: FULL_BUILD_SPEC.md §30. T48 и последующие процессы этим этапом не реализованы. Первоначальный импорт не является открытием магазина: после выбора native старый checkout закрыт, новый будет в T48; интеграция отгрузки/возвратов — T49.

## Формат

Один фиксированный импорт, одна строка на SKU. Утверждённая таблица:
https://docs.google.com/spreadsheets/d/1q5PxNK1_i5FgcpemI3wwRmCwZsww_iMM3j1WIJwVBz4/edit,
вкладка **Инвентаризация**. Импортёр никогда не изменяет таблицу, её данные или доступы.

Точные девять заголовков, в этом порядке:

```text
SKU; Название / модель; Вариант; Количество, шт.; Закупка всего, BYN; Цена дропу за 1 шт., BYN; Ссылка на фото; Описание / характеристики; Примечание / комплектация
```

`Закупка всего` — сумма за всё количество строки, D — цена одной единицы. Пустая закупка при положительном количестве означает неизвестную стоимость. Известный ноль вводится как `0`. Количество обязательно, целое >=0. У пустого физического пула стоимость всегда известный 0: при количестве 0 пустая закупка нормализуется в 0, положительная закупка отвергается. Пустой вариант допустим. SKU: 1–80 латинских букв/цифр/точек/дефисов/подчёркиваний, начало — буква/цифра; регистр значим в сохранённом SKU, дубликаты также ищутся без учёта регистра. Денежные значения: BYN с точкой или запятой, максимум два знака после разделителя; группировка тысяч пробелами допустима. Валютные символы/экспоненты/отрицательные суммы отвергаются. Нет колонки места хранения.

Поддержаны UTF-8 CSV из Google Sheets (включая BOM, кавычки, запятые и переносы строк в тексте) и TSV. XLSX нужно экспортировать в CSV/TSV, отдельного Excel-движка нет. Лимит — 10 000 непустых строк. Ошибка любой строки блокирует весь apply.

## Подготовка файлов и среды

1. Использовать **сверенную физическую инвентаризацию**, а не старый sync snapshot. Для реальной базы отдельно согласовать cutover и резервную копию. Production-перенос этим поручением не разрешён.
2. Экспортировать только вкладку «Инвентаризация»: Google Sheets → Файл → Скачать → CSV (текущий лист). Сохранить файл вне репозитория. Менять утверждённую таблицу для разработки не требуется.
3. Скачать выбранные фотографии из ссылок в отдельную локальную папку. Одна фотография на SKU: `W0001.jpg`, `W0002.png` и т.п.; поддержаны JPEG/PNG/WebP. Две фотографии с одним SKU — неоднозначность и ошибка. Ссылка из строки сохраняется как исходная ссылка, но не используется вместо файла в object storage. Папки Google Drive, страницы просмотра и произвольные URL импортёр автоматически не скачивает. Дополнительные медиа затем загружаются существующей админкой.
4. Для копирования фото настроить существующие `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_ENDPOINT`, `OBJECT_STORAGE_REGION`, `OBJECT_STORAGE_ACCESS_KEY_ID`, `OBJECT_STORAGE_SECRET_ACCESS_KEY`. Секреты не передавать в аргументах команд. Без фото/полного описания/D карточка сохраняется черновиком; импорт никогда сам не публикует даже полную карточку.
5. В существующей целевой БД должны быть применены миграции, настроена BYN через существующий `catalog:bootstrap`, ровно один ACTIVE Supplier и реальный незаблокированный Admin. Для записей нужны одновременно `users.is_admin=true` и Telegram ID актора в текущем `ADMIN_TELEGRAM_IDS`. `--actor` — UUID User, не Telegram ID.

Все команды ниже запускать из корня `C:\Users\novik\OneDrive\Desktop\watch`. Сначала явно задать **нужную локальную/тестовую** `DATABASE_URL`; `.env` подхватывается без переопределения уже заданных переменных. Не копировать адреса тестовых баз в production.

```powershell
$env:DATABASE_URL = 'postgresql://USER:PASSWORD@127.0.0.1:PORT/DISPOSABLE_DATABASE'
$env:INVENTORY_PROVIDER = 'native'
# ADMIN_TELEGRAM_IDS и object storage — из вашей локальной конфигурации.
pnpm build:packages
pnpm --filter @watch/db db:migrate
```

`catalog:bootstrap` при необходимости: `pnpm --filter @watch/api catalog:bootstrap --currency BYN --supplier-name "<реальное имя>"`. Это не импорт часов и не создаёт пользователя Admin. Не вводить выдуманные данные вместо реальной инвентаризации.

## Preview → явное применение

```powershell
pnpm --filter @watch/api inventory preview --file 'C:\Inventory\inventory.csv' --media-dir 'C:\Inventory\photos'
```

Preview ничего не записывает в БД или object storage. Проверить `errors` (должен быть пустым), `warnings`, каждую строку, сопоставления, сумму единиц, `knownCostMinor` и `unknownCostSkus`. `knownCostMinor` — только покрытая стоимость, не полная сумма при неизвестных строках. Сохранить 64-символьное значение `confirmation` из результата.

```powershell
pnpm --filter @watch/api inventory apply --file 'C:\Inventory\inventory.csv' --media-dir 'C:\Inventory\photos' --confirm '<confirmation из preview>' --actor '<UUID существующего Admin>' --reason 'Сверенная первоначальная инвентаризация, документ …' --at '<фактическая ISO-дата, например 2026-10-16T12:00:00+03:00>'
```

Значение `--at` не может быть в будущем. Если фото не готовы, можно опустить `--media-dir` в обеих командах: появятся предупреждения и черновики без медиа. Если файлы, строки или сопоставления изменились, сделать новый preview. Не подставлять придуманный `confirmation`.

Apply перепроверяет данные под блокировками. Точное сопоставление возможно только по SKU и совпадающему external key; сопоставления по названию нет. Коллизия регистра/ключа/названия/варианта, уже инициализированный SKU или существующая опубликованная/архивная карточка блокируют новый импорт и требуют сверки. Общая существующая Product с несколькими Variant также требует сверки, чтобы описание/примечание одного SKU не перезаписало соседний вариант. Импорт не перезаписывает работающий каталог. Существующие DRAFT с единственным Variant и точным сопоставлением можно дополнить через CatalogService; прочие specifications сохраняются. Перед первым cutover не должно быть ACTIVE старых резервов: их нужно штатно сверить/закрыть, а не удалить SQL.

Результат: `initializationId`, `replayed=false`. Повтор **того же файла с первоначальным confirmation** возвращает `replayed=true` даже после новых поступлений: никаких новых карточек/фото/остатков. Новый confirmation или изменённый файл не разрешает переинициализировать ранее принятый SKU. БД и журнал применяются атомарно; при ошибке импортёр компенсирующе удаляет созданные им объекты из хранилища. Как у существующего AssetService, аварийное прекращение процесса между upload и commit может оставить неиспользуемый объект; частично применённого складского факта не будет.

При наличии уже разрешённого Google service account вместо `--file` можно использовать **`--google true`** в preview и apply. Это один read-only запрос строго к утверждённым ID/вкладке, с числовыми значениями без форматирования. Нужен `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON_B64`; при отсутствии доступа использовать CSV. Новые доступы/credentials не выдаются автоматически. Реальные Google-данные в локальной приёмке T47 не читались.

## Последующие поступления и корректировки

Не обновлять старый файл для изменения действующего остатка. У каждой операции — постоянный уникальный `--key`, фактическая дата, оператор и причина. Повтор с теми же параметрами не создаёт движения; изменение параметров с тем же ключом — конфликт.

```powershell
# quantity — принятое количество; cost — ОБЩАЯ сумма в BYN, либо unknown.
pnpm --filter @watch/api inventory receipt --sku W0001 --quantity 2 --cost '160.00' --key 'receipt:<ID документа>:W0001' --actor '<Admin UUID>' --reason '<документ и причина>' --at '<ISO-дата>'

# Списание свободного остатка. Стоимость рассчитывает сервер; unknown здесь
# означает отсутствие вводимой вручную стоимости, а не принудительное обнуление.
pnpm --filter @watch/api inventory correction --sku W0001 --quantity -1 --cost unknown --key 'correction:<ID>' --actor '<Admin UUID>' --reason '<подтверждённая потеря/ошибка пересчёта>' --at '<ISO-дата>'

# Положительная коррекция: quantity >0 и фактическая общая cost либо unknown.
# Полная документированная оценка СВОБОДНОГО текущего пула, без изменения количества:
pnpm --filter @watch/api inventory valuation --sku W0001 --quantity 0 --cost '<полная оценка в BYN>' --key 'valuation:<ID документа>' --actor '<Admin UUID>' --reason '<основание полной оценки свободного остатка>' --at '<ISO-дата>'
```

Нулевое поступление и коррекция без изменения количества отвергаются. Списание не затрагивает зарезервированные единицы. Оценка меняет только текущий свободный базис; историческая неизвестная C в заказах не дополняется задним числом. Известное новое поступление не исправляет неизвестный смешанный пул. Резервы фиксируют floor(V*q/Q), последний — весь остаток; новое поступление не меняет старые allocations.

## Runtime и граница этапа

API/worker: `INVENTORY_PROVIDER=native`. Orchestrator не создаётся, periodic Google reads выключены; readiness требует явный выбор authority. После первого успешного apply возврат к google_sheets/unset отклоняется readiness и защитой external writer в БД. Исторические source-поля и sync runs остаются историей; фиктивные timestamps не записываются. В админке `/admin/inventory` — физическое наличие/резервы/стоимость; кнопки sync в native нет. Поступления/корректировки в T47 выполняются указанной командой, отдельной новой формы нет.

Для production Compose существующие ops-команды автоматически подключают `ops/docker/compose.native.yml`, если в используемом env-файле `INVENTORY_PROVIDER=native`. Overlay убирает Google secret из API/worker/bootstrap. Для ручного `docker compose` нужно явно добавить `-f ops/docker/compose.native.yml` после основного файла. Нужен Compose с поддержкой `!override`/`!reset` (локально проверено 5.1.4). Это проверка конфигурации, не выполненный deployment и не сертификация T52.

T48 должен использовать NativeInventoryService в той же транзакции, что Order/снимки. Для существующего заказа порядок: Partner (если нужен) → Products по ID → Variants по ID → Order → OrderItems → Reservations → InventoryItems по Variant ID. `lockCatalog`/`lockStock` разделены для соблюдения этого порядка. Списание отгрузки и физическая приёмка Return подключаются в T49; старые обработчики не заменяют эти операции. Новая проверка COMMIT не допускает рассогласованные native reservation statuses/journal.
